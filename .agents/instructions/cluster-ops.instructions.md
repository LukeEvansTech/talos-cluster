# Cluster operations: traps that read as something else

Read before running the local linter, querying the live cluster, changing an app's state through its API, or merging a batch of pull requests. Each item is a failure whose symptom points at the wrong cause.

## Linting this repository locally

- **Lint a throwaway sandbox, never the full checkout.** A super-linter run against this repository can hang in file enumeration for 12+ minutes, even with a correctly anchored `FILTER_REGEX_INCLUDE`, because the filter narrows what gets linted, not what gets enumerated. The tell is a log whose last line is `PARALLEL_COMMAND: parallel ...` with nothing after it. Copy the changed files plus `.editorconfig` and `.github/linters/` into a temporary directory, `git init`, commit, and lint that: about 90 seconds, with real per-linter results.
- **Kill a stuck container instead of waiting** (`docker kill`), and check for stale ones first: `docker ps --filter ancestor=ghcr.io/super-linter/super-linter:<version>`. A backgrounded wrapper around a killed run still reports exit code 0, which is not a pass.
- **Prove the run happened.** Capture `LOG_LEVEL=DEBUG` to a file; `grep -c 'Successfully linted'` should be 5 or more and every target path should appear. A filter regular expression is matched against `/tmp/lint/<path>`, so a repository-relative anchor matches nothing and exits 0 having linted nothing.
- **Commit normally from a `git worktree`: lefthook runs there.** Its `Skipping hook sync: core.hooksPath is set locally` box is a warning about reinstalling the hooks, printed while every hook still runs and passes (verified 2026-10-18). Read the summary lines below it before reaching for `--no-verify`.

## Querying the live cluster

- **`kubectl` needs this repository's kubeconfig.** There is no `~/.kube/config`; `KUBECONFIG` is exported only by `.mise.toml` inside the checkout. Elsewhere, a bare `kubectl` fails with `the server could not find the requested resource`, which reads as a broken API server. Set `KUBECONFIG=<checkout>/kubeconfig` (and `TALOSCONFIG=<checkout>/talos/clusterconfig/talosconfig` for `talosctl`).
- **Ad-hoc Prometheus queries:** go through the API-server proxy, `kubectl get --raw "/api/v1/namespaces/observability/services/kube-prometheus-stack-prometheus:9090/proxy/api/v1/query?query=<urlencoded>"`; a port-forward drops mid-session. `/api/v1/alerts` includes pending alerts, so filter on `state == "firing"`.
- **`kubectl logs deploy/<x>` reads one pod.** On a multi-replica Deployment the log is a sample; a missing event may have landed on the other replica. Check `.status.replicas` first, and prefer the sender's own record over a receiver's log.
- **`kubectl run -i --rm` drops the first lines a short-lived pod prints**, because `-i` attaches after the container starts, so a loop's first iteration looks like it never ran. Run the pod without `-i`/`--rm`, `kubectl wait --for=jsonpath='{.status.phase}'=Succeeded`, read `kubectl logs`, then delete it.
- **App APIs from inside the pod.** Sonarr and Radarr carry their key and port as environment variables (`$SONARR__AUTH__APIKEY`, `$SONARR__SERVER__PORT`, likewise `RADARR__`), not in a readable `config.xml`; call `curl` on `localhost` inside `kubectl exec ... sh -c '...'` so the key never leaves the pod. Plex's token is `PlexOnlineToken` in `/config/Library/Application Support/Plex Media Server/Preferences.xml`, and the Plex image ships `curl` and `jq`. Settings changed this way (notification connections, posters) are not in Git: record them in the app's `docs/docs/apps/` page.
- **Jellyfin 10.11 rejects `X-Emby-Token`** with a 401 that reads as a bad key; send `Authorization: MediaBrowser Token="<key>"`. WatchState wants `X-APIKEY` with `WS_API_KEY` from `/config/config/.env`, and its pod has no Python, so parse responses locally.
- **After a live change that writes app state, check the volume and the namespace's alerts.** Provisioning five WatchState identities copied the library state five times (~120M each), filled its 1Gi volume and served 503s for an hour while `KubePersistentVolumeFillingUp` fired unseen (2026-10-18). Run `df -h` on the mount, then the firing-alerts query above filtered to the namespace.
- **Keep `kubectl exec ... sh -c` scripts literal and free of `rm`.** Claude Code's removal check blocks a script it cannot read (`sh -c "$(cat file)"`) and some without `rm` at all; free space with `find ... -exec truncate -s 0 {} +`, and pipe secrets on stdin with `IFS= read K`, since `head -1` swallows the rest of the stream.

## Merging batches of Renovate pull requests

- **Wait on the right check rows, not a merged PR's `gh pr checks` list.** That list mixes rows every pull request gets, path-filtered rows, and skipped jobs. The `main` ruleset requires exactly one status, `claude/renovate-review`; classic branch protection requires none. `claude/renovate-review` is posted on every pull request, and it passes at once on one Renovate did not open. Everything else below is convention, kept in `.github/merge-rows`, which a merge wait should read before adding the rows below.
- **Rows for every pull request:** `lint / lint`, `Konflate`, `Internal Identifier Scan`, `Checkov`, `Trivy`, `GitGuardian Security Checks`, `Scan PR title and body`, `Scan commit authorship` (the `.github/merge-rows` set), plus the required `claude/renovate-review`. `review / Breaking Change Analysis` also runs on every pull request, as the job that posts that status. A manifest change under `kubernetes/` adds nothing to this set.
- **Extra rows for a change under `docs/`:** `Docs pages linked`, `docs / build` and `drift / drift`. `docs / deploy`, `docs / link-check` and `docs / prose` are always skipped on a pull request; never wait on them. `drift / drift` also runs for any change under `.github/workflows/`, to `.renovaterc.json5` or to `.markdownlint.yml`; `Docs pages linked` for `.github/scripts/check_docs_linked.py`; and each path-filtered workflow for an edit to its own file. A change to the curator apps' `app/resources/` adds `Curator engine tests (curator)` and `Curator engine tests (curatortv)`, one row per matrix entry.
- **Rows for a Renovate pull request:** the same set, and here `claude/renovate-review` is the real gate. `Scan PR title and body` reads skipped, which is not a failure.
- **`mergeable` goes `UNKNOWN` on every other open pull request after each merge**, because GitHub recomputes it asynchronously. A guard of `mergeable == MERGEABLE` read straight after a merge silently skips the rest of the batch. Poll `gh api repos/<owner>/<repo>/pulls/<n> --jq .mergeable` until it is not `null` (that REST read triggers the recompute), and retry once on `Base branch was modified`.
- **Drop `--delete-branch`.** It costs roughly 150 REST calls per merge and can empty the hourly budget within a batch; branches are deleted on merge by repository settings anyway.
- **REST and GraphQL are metered separately.** With REST at zero, `git push`, `gh pr merge --squash` and `gh api graphql` still work; check `gh api rate_limit` for `.resources.graphql`.
